Reproducibility checklist for AI research

A practical reproducibility checklist for AI research: data, code, environment, model versions, seeds, prompts and evaluation — so a result can be checked, not just believed.

In short: A reproducible result is one someone else can re-run and get the same answer. This guide is a 29-item checklist — data, code, environment, model, prompts, evaluation, claims and documentation — you can run on your own work before you submit it, and on any paper you are about to cite or build on. A “no” on any item is not a failed paper; it is a named gap, and the gap should be recorded, not hidden.

A reproducible result is one that someone else can re-run and get the same answer — using the same data, the same code, the same model and the same settings. Most AI research fails this test, not because the authors are dishonest, but because the pieces a re-run needs were never written down: the dataset version, the model version, the random seed, the exact prompt, the evaluation script. A citation is the visible half of reproducibility; data, code, versions and seeds are the other half.

This guide gives you a checklist you can run on your own work before you submit it, and on any paper you are about to cite or build on. A reader who never contacts Oryx should still leave able to do the check.

Why AI research is hard to reproduce

AI research has four failure modes that older fields mostly do not:

  1. The model moves. A result produced with a hosted model in March may not reproduce in June, because the provider updated the model behind the same name. A model name is not a version.
  2. The prompt is missing. For work that uses a language model, the prompt is part of the method. A paper that reports results but not the exact prompt cannot be re-run.
  3. The data is described, not shared. “We used public data” is not enough. Which version, which split, which filtering, which exclusions — each of those changes the result.
  4. Randomness is unrecorded. Training runs, sampling and data shuffling all depend on seeds. Without the seed and the sampling settings, the same code can give a different answer.

The citation problem Oryx has measured is the same pattern one level down: in a published pilot audit of 66 AI-generated citations, 31 (47%) had broken links, 7 (11%) mismatched the claim, 11 (17%) could not be verified, and only 5 both resolved and fully supported the claim (Paper 2, study 1 — a pilot, not a universal rate). In the larger audit behind that paper, 194 citations across 30 AI research briefs were checked: 50 verified, 95 broken, 17 mismatched, 31 unverifiable, and 1 with no URL at all. A citation that cannot be found is a reproducibility failure in miniature — and it is the easiest one to catch before submission.

The checklist

Work through the list in order. A “no” on any item is not a failed paper; it is a named gap, and the gap should be recorded, not hidden.

1. Data

  • ☐ The dataset is named with its exact version, and the source is given (a link, a DOI, or a repository — not just a name).
  • ☐ The train/validation/test split is stated, including the sizes of each split and how the split was made (random seed, stratified, by time, by source).
  • ☐ Any filtering, cleaning or exclusion is described — what was removed, and why.
  • ☐ If the data cannot be shared (privacy, licence, commercial terms), that is stated, and a sample or a full description of the schema is provided instead.
  • ☐ The data as used in the experiments is archived somewhere stable, not only on the author’s laptop.

2. Code

  • ☐ The code that produced the reported numbers is shared, or the reason it cannot be shared is stated.
  • ☐ The repository is tagged at the exact commit used for the reported results — “the current code” is not a version.
  • ☐ The steps to run it are written down: one command, or a short numbered list, that a stranger can follow.
  • ☐ Dependencies are pinned (a lockfile or a requirements list with versions), not “install the latest”.

3. Environment

  • ☐ The hardware is stated where it matters (GPU model, memory) — training time and batch size depend on it.
  • ☐ The software environment is recorded: operating system, language version, library versions.
  • ☐ If the work ran on a hosted service, the service and the date of the run are recorded — hosted services change without notice.

4. Model

  • ☐ The model is identified by exact version, not just by family name (“gpt-4” is a family; the version string is the identifier).
  • ☐ If the model was fine-tuned, the base model, the training data, and the training settings are stated.
  • ☐ If the model was accessed through an API, the API version and the date of access are recorded.

5. Prompts and settings

  • ☐ Every prompt used is reproduced in full — system prompt, user prompt, and any few-shot examples.
  • ☐ Sampling settings are recorded: temperature, top-p, maximum tokens, and any other parameter that changes the output.
  • ☐ The random seed (or seeds) is recorded for every stochastic step: training, sampling, shuffling, and data splitting.

6. Evaluation

  • ☐ The evaluation metric is named and defined — not just “accuracy”, but accuracy on what, computed how.
  • ☐ The evaluation set is identified separately from the training set, and its size is stated.
  • ☐ The evaluation script is shared, or its logic is described in enough detail to rebuild it.
  • ☐ Results are reported with their variability where it exists: multiple seeds, standard deviation, or a range — not a single best run.

7. Claims and evidence

  • ☐ Every substantive claim in the paper points at a specific result, table, or figure — not at the paper in general.
  • ☐ Every citation resolves: follow each DOI or link and confirm it lands on the paper cited. In Oryx’s pilot audit, 47% of AI-generated citations did not resolve at all — check yours before a reviewer does.
  • ☐ Every citation actually supports the claim it is attached to. A real paper cited for a claim it does not make is a failed check, not a pass.
  • ☐ Negative results and failed attempts that bear on the claim are reported, not omitted.

8. Documentation

  • ☐ The paper states what was tried and discarded, where that changes the interpretation of the result.
  • ☐ Known limitations are written down — including what was not tested and what would change the conclusion.
  • ☐ Contact details for the code and data are given, and someone is named as responsible for answering questions about them.

How to use the checklist on someone else’s paper

You do not need the authors’ cooperation to run a useful version of this check. Before you cite a paper or build on it:

  1. Check the citations first. Follow five citations at random. If two do not resolve or do not support their claims, treat the paper’s evidence as unverified until you have checked more. This takes ten minutes and catches the most common failure.
  2. Look for the version strings. Search the paper for the model version, the dataset version, and the code repository. If none of the three is present, the paper cannot be re-run as written.
  3. Look for the seed and the prompt. If the work used a language model and neither the prompt nor the sampling settings appear, the results are a description of one run, not a reproducible method.
  4. Check whether the evaluation set is separate from the training set. If the paper does not say, do not assume it is.
  5. Record what you found. One line per paper: what you checked, what was missing, and whether you are relying on it anyway. That record is your defence if the result turns out not to hold.

How to use the checklist on your own work

Run the checklist the day you finish the experiments, not the day you submit. Three habits make the difference:

  • Freeze as you go. Tag the code commit and record the model version and seed at the moment each result is produced. Reconstructing them weeks later is where most gaps appear.
  • Re-run once from a clean copy. Clone the repository fresh, follow your own instructions, and confirm the headline number comes out the same. If you cannot reproduce your own result, nobody else can.
  • Keep a one-page reproducibility note with the paper. Dataset version, code commit, model version, seed, prompt, evaluation script, and the date of the run — one page, attached to the submission or the repository. It costs an hour and it is the single most useful page a reviewer or a future collaborator will read.

Common traps

  • “The code is available on request.” Code that is available on request is usually code that is never requested — and often code that no longer runs. Shared, tagged, and runnable beats promised.
  • A version number that is actually a family name. “GPT-4”, “Llama 3”, “Claude” are families. The version string, the API date, or the checkpoint hash is the identifier.
  • One seed, one run, reported as the result. A single run is a sample of one. If you ran it once, say so — and say what the variability would be if you knew it.
  • A real citation for a claim it does not make. The most common citation failure after broken links: the paper exists, the link works, and the claim is not in it. Check support, not just resolvability.
  • The evaluation that tests what was trained on. If the test set leaked into training, the number is meaningless. State the split and how it was protected.
  • “Reproducible” claimed, “replicable” meant. Reproducing means the same data and code give the same result. Replicating means new data gives the same conclusion. Do not claim one when you have done the other.
